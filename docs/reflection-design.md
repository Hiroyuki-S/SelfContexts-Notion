# 振り返りシステム 設計メモ

## 0. 目的

「日記を書く」ことではなく、**自分を知り → 強みを活かし → 弱みを改善する**ための
データを継続的に貯めることが目的。そのために3つの原則を置く。

1. **毎回おなじ軸で聞く** — 比較できないログは分析できない。質問は固定、答えは自由。
2. **ログと結論を分ける** — 生の記録（振り返りログ）と、そこから抽出した自己理解
   （自己理解台帳）を別DBにする。台帳こそが最終成果物で、ログはその根拠。
3. **記録は飛ぶ前提で組む** — 歩くのは平日だけ、答えられない日もある。
   欠損が混ざっても壊れない集計にし、途切れたことを咎めない。

```
日次(3分/平日) ─┐
週次(15分) ─────┼─→ 振り返りログDB ──抽出──→ 自己理解台帳DB
月次(30分) ─────┤                            （強み/弱み/価値観の仮説と検証状態）
四半期(60分)────┘                                      │
                        目標DB ←──レビュー──────────────┘
                （人生目標 / 中長期目標 / 短期目標）
```

## 1. 日次（平日の夜の散歩・約3分・音声）

毎回おなじ5問。散歩しながら口頭で答えられる長さに抑える。

| # | 質問 | これで何を取るか |
|---|------|-----------------|
| 1 | 今日いちばんエネルギーが上がった瞬間は？ | 強み・情熱の在りか（何をしている時の自分が強いか） |
| 2 | 逆に、いちばん消耗した・気が重かった瞬間は？ | 消耗源・弱みのトリガー |
| 3 | 今日の自分の判断や動きで「これは自分らしい」と思えたことは？ | 強みの発露（無自覚に出ている癖＝才能の候補） |
| 4 | うまくいかなかったこと。なぜそうなったと思う？ | 失敗のパターン。「なぜ」まで一言添えるのが肝 |
| 5 | コンディション：エネルギー / 集中 / 気分（各1〜5） | 数値。後から相関を見る唯一の定量軸 |

- 1〜4は各1〜2文でよい。言い淀んでもそのまま記録する（取り繕わない）。
- 最後にClaude側で**キーワードを3つ**自動抽出してタグ化する（人・場所・活動・感情）。
- 答えられない日は「パス」でよい。空欄で記録し、継続を優先する。
- 日次では**目標に触れない**。毎日問うと目標が義務になる。

### 日次で聞かないこと（意図的に外したもの）
- ToDoの消化率 → タスク管理の仕事であり、自己理解には効かない
- 感謝リスト → 効果はあるが定型化しやすく、5問を圧迫する（週次に回す）
- 長期目標の進捗 → 日次で問うと焦りを生む。週次以降で扱う

## 2. 記録が飛ぶ前提での設計

歩くのは基本的に平日のみ。歩かない日・答えられない日がある。
これを例外扱いせず、最初から仕様に織り込む。

| 論点 | 決めたこと |
|------|-----------|
| 対象日 | 記録した日時ではなく**振り返る対象の日**を持つ。深夜0時以降の記録は前日扱い |
| まとめ記録 | 複数日をまとめて話した場合も、日ごとに別ページを作る（1ページに混ぜない） |
| 遡り | こちらから未記録日を掘り起こさない。本人が言い出したときだけ |
| 集計の母数 | 記録がある日だけ。欠損日を0や平均値で埋めない |
| 記録日数 | 週次以降に事実として記録するだけ。少なさに言及しない |
| ストリーク | **追わない。** 連続記録を評価軸にすると、途切れた時点でやめたくなる |
| 日次0件の週 | 週次は実施する。要約提示を省き、記憶ベースで3問に絞る |

## 3. 週次以降の骨格

週次・月次・四半期は共通して次の順で進む。

```
得たい結果 → やったこと → Good / Bad → 要因分析 → 次の目標
```

この順序には理由がある。

- **得たい結果を先頭に置く** — ログの要約から始めると振り返りが近況報告になる。
  基準点を先に置くと「得たい結果との差分」の話になる。
  ただし毎回ゼロから書かせない。目標DBの該当階層を提示して「これで合ってる？」と確認する。
  毎週書き直すと、その週の気分で目標が揺れる。
- **やったことは本人に思い出させない** — 日次ログから一覧を組み立てて提示し、抜けを足してもらう。
  日曜の夜にゼロから1週間を思い出すのは負荷が高く、そこで力尽きると要因分析に届かない。
- **要因分析が核** — Good/Badの列挙で終わらせない。時間が足りないときは
  やったことの確認や自己評価を削り、要因分析に回す。
- **「強みは何？」と直接聞かない** — 強みは「なぜうまくいったか」の答えの中にしか現れない。
  直接聞くと、本人が「強みらしいこと」を探して答えるようになる。
  本人には事実と理由だけを話してもらい、強み・弱みとして言語化するのはClaude側の仕事。
  言語化した結果は台帳に書き、次の振り返りで「この見立て、合ってる？」と検証にかける。

扱う目標の階層は振り返りの粒度で変わる（週次=短期、月次=中長期、四半期=人生目標）。

## 4. 週次（日曜夜・約15〜20分）

1. （短期目標を提示）今のあなたが得たい結果は、これで合ってる？
2. （やったこと一覧を提示）今週やったことはこの通り。抜けている大きなものは？
3. 今週のGoodは？
4. 今週のBadは？
5. **そのGoodは、なぜ起きた？ 自分の何が効いた？ 条件は何だった？**
6. **そのBadは、なぜ起きた？ 何があれば防げた？**
7. 先週立てた実験の結果は？
8. 得たい結果に近づくために、来週の目標をひとつ決めるとしたら？
9. その目標のために、来週ひとつだけ試すことは？
10. 今週の自己評価（1〜5）と理由

5と6が要因分析。ここが一番厚い。
8の「目標」と9の「実験」は別物として両方置く（目標=達成したい状態、実験=試す行動）。

→ **アウトプット**：週次ログ1件、自己理解台帳の追記・更新1〜3件、短期目標の更新。

## 5. 月次（月末・約30分）と四半期（3ヶ月ごと・約60分）

骨格は週次と同じで、スケールと固有の問いが変わる。

**月次で追加されるもの**
- **条件の棚卸し**：今月、自分が強かった条件と弱かった条件は何だったか
  （時間帯・人数・締切の有無・場所・体調）
  週次の要因分析を4週分ならべると、条件のパターンが見えてくる。
  強みは「条件」とセットで初めて使えるので、ここが月次の核。
- 強み仮説の更新、弱みへの対策の有効性判定
- 中長期目標のレビュー（短期目標との整合）

**四半期で追加されるもの**
- **要因の要因**：3ヶ月スパンで見て、繰り返し出てくる要因は何か。
  月次までは個別の要因分析。繰り返し出る要因こそ台帳に昇格すべき自己理解。
- 台帳の書き直し（確信に変わったもの／棄却するもの／表現を変えるもの）
- 価値観の確認、人生目標のレビュー（今も本心か、言い方を変えたくなっていないか）
- 1年前の自分との差分、次の四半期のテーマ

## 6. Notion データ構造

既存の「📓 日記」は自由記述の場としてそのまま残し、振り返りは
**🪞 SelfContexts** ページ配下の新規3DBで運用する。

### DB1: 🌙 振り返りログ

`data_source_id: 2923cd5a-9b5e-460a-99ff-e7d6484147aa`

| プロパティ | 型 | 備考 |
|-----------|-----|------|
| Name | title | `2026-09-16 (火) 日次` / `2026-W38 週次` |
| 種別 | select | 日次 / 週次 / 月次 / 四半期 |
| 対象日 | date | 週次以降は期間（開始〜終了） |
| エネルギー / 集中 / 気分 | number | 各1〜5（日次） |
| 自己評価 | number | 1〜5（週次以降） |
| 記録日数 | number | 週次以降。期間内に日次ログが何件あったか |
| キーワード | multi_select | Claudeが自動抽出（3つ程度） |
| 次の実験 | rich_text | 次の振り返りまでに試すこと |
| 実験の結果 | select | 未実施 / 実施 / 部分的 / 対象外 |
| 入力元 | select | 音声 / 手入力 / フォーム |
| 関連する自己理解 | relation → DB2 | この回で更新した自己理解 |
| レビューした目標 | relation → DB3 | この回でレビューした目標 |

ページ本文に Q&A をそのまま見出し付きで記録する（生の言葉を残すことが重要）。

### DB2: 🧭 自己理解台帳

`data_source_id: 5c29b421-d5cd-41ff-9094-6b01187cd108`

1行 = 自分についての仮説ひとつ。これが蓄積されていく資産。

| プロパティ | 型 | 備考 |
|-----------|-----|------|
| Name | title | 仮説を一文で（例:「初動の遅さは情報不足ではなく失敗予期から来る」） |
| 分類 | select | 強み / 弱み / 価値観 / エネルギー源 / 消耗源 / 思考のクセ / 環境条件 |
| 状態 | select | 仮説 / 検証中 / 確信あり / 更新済 / 棄却 |
| 確信度 | number | 1〜5 |
| 活かし方・対策 | rich_text | 強みなら使いどころ、弱みなら回避・補完策 |
| 次の実験 | rich_text | この仮説を検証する具体行動 |
| 根拠となる振り返り | relation → DB1 | 元になった振り返り（複数） |
| 関連する目標 | relation → DB3 | この自己理解が効く目標 |
| 初出 / 最終更新 | date / last_edited_time | |

更新は**週次以降のみ**。1日の出来事で仮説を立てると、その日の気分に引きずられる。
**棄却を残すのが要点**。「違った」という記録が自己理解の精度を上げる。

### DB3: 🎯 目標

`data_source_id: f3428b4c-f911-4771-9183-5f187439a31d`

| プロパティ | 型 | 備考 |
|-----------|-----|------|
| Name | title | 目標を一文で |
| 階層 | select | 人生目標 / 中長期目標 / 短期目標 |
| 状態 | select | 構想中 / 進行中 / 達成 / 見直し中 / 取り下げ |
| レビュー頻度 | select | 週次 / 月次 / 四半期 ← **どの振り返りで扱うかを決める** |
| なぜこれをやるのか | rich_text | 動機。迷ったときに立ち返る場所 |
| 達成の目安 | rich_text | どうなったら達成と言えるか |
| 期限 / 進捗 | date / number | 進捗は0〜100 |
| 次の一手 | rich_text | |
| 最終レビュー | date | レビューのたびに更新 |
| 親目標 / 子目標 | relation（自己参照） | 短期→中長期→人生 とぶら下げる |
| 関連する自己理解 | relation → DB2 | この目標に効く強み・立ちはだかる弱み |
| 関連する振り返り | relation → DB1 | |

**レビュー頻度プロパティが、目標と振り返りをつなぐ蝶番**になる。
短期目標は週次、中長期は月次、人生目標は四半期でしか触らない。
人生目標を毎週問うと疲れるし、短期目標を四半期にしか見ないと形骸化する。

**関連する自己理解のリレーション**が、この構成のもう一つの要。
「この目標が進まないのは、この弱みが効いているから」を構造として持てる。

## 7. 仕組み（どう「聞いてきてもらう」か）

入力方式は **スマホのClaudeアプリに音声で話す** を主軸にする。

```
平日 21:30  Routineが発火 → 通知「今日の振り返り、いきますか？」
  ↓
散歩しながら Claude に音声で応答（1問ずつ返ってくる）
  ↓
5問終了 → Claudeがキーワード抽出・数値整形
  ↓
Notion MCP で 振り返りログDB に1ページ作成
  ↓
（週次以降）過去ログを読み込んで要約 → 対話 → 台帳DB・目標DBを更新
```

### 構成要素

| 要素 | 置き場所 | 役割 |
|------|---------|------|
| `.claude/skills/reflection/questions.yaml` | このリポジトリ | 4種類の質問セット（唯一の正） |
| `.claude/skills/reflection/SKILL.md` | 同上 | 聞き方・欠損の扱い・Notion書き込み手順 |
| Routine（定期実行） | Claude Code Remote | 平日夜・日曜夜・月初・四半期初に起動 |
| Notion 3DB | 🪞 SelfContexts 配下 | 保存先 |

質問文はすべて `questions.yaml` に集約し、運用しながら育てる。
「この質問、答えにくい」と思ったらそのファイルだけ直せばよい状態にする。

## 10. 目標の初期登録（2026-09-17）

```
人生目標（期限 2049-03-31）
「何にも縛られずに働き、田舎の本拠地とキャンピングカーの旅を行き来しながら、
  季節と自然とともに暮らしている」
  │
  ├─ 💰 資産からの収入だけで生活費をまかなえる状態をつくる  ← 進行中
  │    └─ 📊 資産と生活費の現在地を数字で把握する（〜2026-12-25・週次）
  ├─ 💻 場所を選ばず、自分が選んだ仕事で稼げる状態をつくる  ← 構想中
  ├─ 🌾 田舎（群馬 or 仙台）に本拠地を構え、季節とともに暮らす  ← 構想中
  ├─ 🚐 キャンピングカーで旅を続けられる体制をつくる  ← 構想中
  └─ 👪 家族と、この暮らし方を一緒に望める関係でいる  ← 進行中
       └─ 🗣️ 家族に構想を話し、どう思っているかを知る（〜2026-12-25・週次）
```

分解にあたって置いた判断：

- **手段は固定しない。** 「リモートか、ネット上の何か」は23年で必ず変わる。
  固定するのは「場所と時間に縛られない」という条件のほうで、手段は中長期目標側で更新する。
- **💰は時間が最も強く効く。** 23年の複利が乗るため、開始が早いほど後が楽になる。
- **👪だけ性質が違う。** 他4つは積み上げて到達するものだが、これは日々の関わりでしか得られず、
  今日から毎日効いてくる。日次の振り返りの材料がそのままこの目標に効く。
- **🚐は「まずレンタルで試す」から入る。** 23年後の暮らし方を一度も体験せずに目指すのは危うい。
  合わないと分かったらビジョンを修正する材料になる。
- **👪の短期目標は「賛成を取り付ける」を達成条件にしない。** 賛成をゴールにすると説得になり、
  相手の本当の考えが出てこなくなる。知ることが目的。

中長期目標の「達成の目安」は `※要記入` のまま。金額や時期は現在地が分かってから決める。

## 9. 定期実行（Routine）

| Routine | スケジュール（JST） | trigger_id |
|---------|-------------------|-----------|
| 🌙 日次の振り返り | 平日 21:30 | `trig_01T71AByxKHjPZ3nMNprSdpV` |
| 📘 週次の振り返り | 日曜 20:00 | `trig_01BU8oYbyJA3kxXj2wQgHieu` |
| 📙 月次の振り返り | 毎月1日 20:00 | `trig_01MxHzaePkdfemv9dWPBzqbz` |
| 📕 四半期の振り返り | 1/4/7/10月の2日 20:00 | `trig_01CuWBEpoMBivMnG3gFaB2VL` |

いずれも発火のたびに新しいセッションを作り、プッシュ通知を出す。

### 既知の制約（Notionコネクタ）※対応済み

Routine を CLI から作成・更新しても **Notionコネクタを付与できない**。
`connectors` パラメータが組織設定で無効化されており、
`the connectors parameter is not available for this organization` が返る（確認済み）。

このままでは発火したセッションに `mcp__Notion__*` ツールが無く、Notionに書き込めない。
**2026-09-17に下記の手順で対応済み**（4本すべて Notion のみを含む状態）。
Routineを新規作成・作り直した場合は、同じ手順を再度行う必要がある。

**対応（claude.ai の画面での操作が必要）**

1. https://claude.ai/customize/connectors で Notion が接続済みか確認する
   （ここに無いコネクタは Routine の選択肢にも出てこない）
2. https://claude.ai/code/routines を開く
3. 対象のRoutineをクリック → 詳細ページで鉛筆アイコン → **Edit routine**
4. Instructions の下にある **Connectors** セクションで Notion を含めて保存
5. 4つのRoutineすべてで繰り返す

注意点：

- **Notion以外のコネクタは外す。** Routineに含めたコネクタは実行中に
  確認なしで書き込みを含む全ツールが使える。振り返りに必要なのは Notion だけ。
- **ネットワーク許可リスト（Allowed domains）の変更は不要。**
  コネクタ通信はAnthropicのサーバー経由で、環境のネットワーク経路を通らない。
- **実行ログの緑色は成功を意味しない。** 「セッションがエラーなく終了した」だけで、
  コネクタが無くて保存できなかった場合も緑になる。設定後は詳細ページの
  **Run now** で1回流し、セッションを開いてNotionツールが呼べているか確認する。

ローカルのターミナルからは `/schedule update` でも変更できる
（クラウドセッション内では `/schedule` は使えない）。

この操作をしない場合、Routineは「質問はできるが保存はできない」状態になる。
その場合の回避策として、振り返り自体はコネクタを持つ通常のセッションから
「振り返り」と話しかけて実行し、Routineは通知役に留める運用も可能。

### 前提

Routineが作るセッションは既定ブランチをクローンするため、
`.claude/skills/reflection/` が main にある必要がある。**マージ済み**（2026-09-17）。
各Routineのプロンプトには、スキルが読めなかった場合のフォールバックとして
手順とDB IDを直書きしてある。
