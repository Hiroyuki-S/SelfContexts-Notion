# 家計BS/PL 設計メモ

## 0. 目的

家計簿をつけることが目的ではない。人生目標「何かに縛られて働く必要がない状態」に対して、
**今どこにいて、あと何年かかるか**を数字で出すための計器をつくる。

短期目標「資産と生活費の現在地を数字で把握する」の実行手段でもある。

## 1. 扱わないもの

**銀行・証券・カードの認証情報は一切扱わない。**
技術的にできないという話ではなく、やってはいけない。会話に認証情報が残るうえ、各社の規約にも反する。
口座への接続はマネーフォワード側の仕事とし、こちらはエクスポートされたCSVだけを扱う。

## 2. データの取り込み方

**マネーフォワードのCSV出力はプレミアム限定**（無料版は連携4口座・閲覧1年までの制限もある）。
課金を前提にしない設計にするため、3通りの入口を用意し、どれで来ても同じDBに入るようにした。

| | 経路 | 費用 | 向いている場合 |
|---|------|------|--------------|
| ① | **転記モード**（既定） MFの集計画面の数字を月1回聞く | 無料 | まず始めるとき。口座4件以内 |
| ② | MF CSV → Googleドライブ → `aggregate.py` | 要課金 | 口座が5件以上、手間を減らしたい |
| ③ | 各社CSV → Googleドライブ → 金融機関別の対応表 | 無料 | 口座が2〜3件 |

**採用したのは③。** 口座は5つで無料枠（4つ）を超えるが、明細レベルで要るのは2つだけのため。

| 口座 | 必要なもの | 扱い |
|------|-----------|------|
| メイン銀行 | 明細（給与・生活費の引落） | CSVを読む |
| カード | 明細（変動費の大半） | CSVを読む |
| マンション運用の銀行 ×2 | 家賃入金、ローン返済、管理費 | 月に数件。入出金を拾うだけ |
| 証券 | 残高と配当額 | 明細不要 |

書くパーサは2つ、毎月のダウンロードも実質2回で済む。各社で列構成が違うため、
新しい金融機関のCSVは列を確認してから対応表を作る（出金・入金が1列か2列かを
間違えると符号が反転する）。

```
① MFの集計画面 ──読み上げ/スクショ──┐
② MF CSV ──────aggregate.py───────┼──→ 📈 家計サマリー（月次）DB
③ 各社CSV ─────金融機関別の対応表──┘
```

**明細はNotionに入れない。** 月に数百行あり、入れるとDBが重くなる。
振り返りで見たいのは推移と指標であって個別の取引ではないため、明細はCSVのまま残す。

### 精度について

**桁が合っていれば計器として機能する。** 到達予測年に効くのは年間支出・純資産・不労所得の
3つで、どれも粗い数字でよい。「月25万か26万か」は結果をほとんど変えないが、
「月25万か40万か」は大きく変える。

正確さを求めて手が止まるのが最悪の結果。分からない項目は **0ではなく空欄**にする
（0だと「支出がなかった」と「把握していない」が区別できなくなる）。

## 3. Notion DB

### 📈 家計サマリー（月次）

`data_source_id: afde1ecc-1729-49ad-9a17-a3a7f39d7490`

1行 = 1ヶ月。PL（期間）とBS（月末時点）を同じ行に持つ。

| 区分 | プロパティ |
|------|-----------|
| 収入 | 給与 / 賞与 / 配当 / 家賃収入 / その他収入 / 収入合計 |
| 支出 | 住居費 / 水道光熱費 / 通信費 / 保険 / 教育費 / 食費 / 日用品 / 交通費 / 娯楽・交際費 / 税・社会保険 / その他支出 / 支出合計 |
| 収支 | 収支 / 貯蓄率 |
| 資産 | 現金預金 / 証券 / 年金資産 / 不動産評価額 / その他資産 / 資産合計 |
| 負債 | 住宅ローン残高 / その他ローン / カード未払 / 負債合計 |
| 指標 | 純資産 / 不労所得 / **不労所得カバー率** / **到達予測年** |
| 管理 | 対象月 / データ元 / メモ |

合計や比率は **Notionの数式ではなく、書き込み時に計算した値を入れる**。
数式は空欄の扱いでつまずきやすく、値が見えないとデータの持ち出しもしにくいため。
手で値を直したときは合計も直す必要がある。

## 3.5 不動産は生活費と必ず分ける

マンション運用が2件あるため、家賃収入には経費（ローン返済・管理費・修繕積立金・固都税・保険）が
対応している。混ぜると2つの数字が壊れる。

- **生活費** = 支出合計 − 不動産経費 … 自分が暮らすのに要る額。カバー率の分母になる
- **不動産純収益** = 家賃収入 − 不動産経費 … 到達予測年に効くのはこの純額

**総額の家賃収入だけで計算すると、到達予測年が10年前後も前倒しに出る。**
同じ前提で試算したところ 2035年 と 2045年 の差が出た。計器として使えなくなる誤りなので、
`projection.py` は経費が0のまま家賃収入だけ入っていると警告を返す。

不動産の収支が赤字の場合も警告を返す。その場合も事実を伝えるだけで、売却などは促さない。

## 3.6 3つの財布を分ける

**生活費 = 支出合計 − 不動産経費 − 副業経費**

| | 収入 | 費用 | 純額 |
|---|------|------|------|
| 生活 | 給与・賞与 | 生活費 | 収支 |
| 不動産 | 家賃収入 | 不動産経費 | 不動産純収益 |
| 副業 | 副業収入 | 副業経費 | 副業純利益 |

不労所得カバー率の分母は生活費。ここに事業の経費を混ぜると分母が膨らみ、
到達予測年が実際より遠く出る。逆に収入側で相殺すると、どちらの事業が
黒字なのか見えなくなる。必ず3つに分けて持つ。

## 3.7 不動産投資のモデル

運用方針は**「基本的に赤字で節税。値上がりすれば売却益、家賃を上げれば収益化」**。
現金収支の赤字は設計どおりであって異常ではない。測るべきは赤字の有無ではなく、
赤字を上回るリターンが出ているか。

```
不動産実質リターン ＝ 元金返済 + 節税効果 + 含み損益の増加 − 現金赤字
```

| | 要素 | 取得元 | 頻度 |
|---|------|-------|------|
| ① | 現金収支（マイナス） | 家賃 −（管理費 + ローン返済） | 月次 |
| ② | 元金返済 | 返済のうち元金分 | 月次 |
| ③ | 節税効果 | 確定申告での税の減少額 | 年1回 |
| ④ | 含み損益 | 評価額 − ローン残高の変化 | 年1回 |

④は自分で動かせず、かつ金額が最も大きくなりうる。年1回は必ず評価額を更新する。
更新が途絶えると、モデルが機能しているか判定できなくなる。

**`不労所得カバー率` に家賃を単純に足さない。** ローン完済までは家賃が不労所得に
なっていないため、足すとカバー率が実態より高く出る。完済後に初めて
「家賃 − 管理費」が不労所得として効いてくる。

サブ口座2つからの各1本。当初「物件2件」と想定して設計したが、

```
年間の現金収支   −565,780
年間の元金返済 +1,943,352 （物件Bの内訳は不明のため未計上）
年間の節税効果   +347,080 （2026/4/16 トヨタ税務署からの還付・実績）
────────────────────────
               +1,724,652 円/年
```

**元金返済がリターンになるのは、物件の評価額が下がらない場合に限る。**
評価額が元金返済より速く下がれば純資産は増えない。
だから年1回の評価額更新が、このモデルの成否を判定する唯一の手段になる。

### 人生目標の期限（2049年3月）時点

最終返済は2060年。**2049年3月の時点でローンは完済していない。**
オリックス4本だけで残高は約 **40,421,657円** の見込み（利率2.150%で試算）。

完済を待つ形では目標年に間に合わないため、出口は売却になる。

```
売却時の手取り目安 ＝ 物件評価額 − ローン残高 − 譲渡税
```

## 4. 見るべき3つの指標

| 指標 | 定義 | 意味 |
|------|------|------|
| 貯蓄率 | 収支 ÷ 収入合計 | 到達スピードを決める |
| **不労所得カバー率** | (配当+家賃収入) ÷ 支出合計 | **100%になった月が「何かに縛られて働く必要がなくなった」日** |
| **到達予測年** | 試算値 | 今のペースでカバー率100%に届く年 |

到達予測年が最も重要。目標は2049年3月なので、予測年がそれより手前なら余裕があり、
後ろなら軌道修正の材料になる。**単月で一喜一憂せず、四半期で3ヶ月分を並べて傾向を見る。**

## 5. スクリプト

### `aggregate.py` — MF CSV → 月次集計

数百行の合計をLLMが目で計算すると誤りが出るため、決定的に動くコードにしてある。

処理の要点：

- 文字コードは `utf-8-sig` → `cp932` → `utf-8` の順で判定（MFはShift-JISで出すことがある）
- `計算対象 != 1` の行を除外（本人が集計対象外にしたもの）
- **`振替 == 1` の行を除外** — 自分の口座間の移動は収入でも支出でもない
- **大項目「現金・カード」を除外** — ATM出金やカード引落を支出に数えると二重計上になる
  （出金と、そのお金で買った物の両方を数えてしまう）
- 金額の符号で収入／支出を判定する（大項目の分類より符号を優先）
- **未知の大項目は黙って「その他」に寄せず、警告として返す**
  寄せてしまうと支出の中身が見えなくなり、要因分析ができなくなる

### `projection.py` — 経済的自立までの年数

`必要金融資産 = (年間支出 − 年間家賃収入) ÷ 取り崩し率` に、現在の金融資産と年間貯蓄を
複利で積み上げて到達年を出す。家賃収入は資産を取り崩さずに得られるので、その分だけ必要額が下がる。

前提はすべてコマンドライン引数で見えるようにしてある（既定：利回り5%、取り崩し率4%）。

**この数字の限界を必ず添えること：**

- 取り崩し率4%は米国株の過去データに基づく経験則。日本の税制・為替・年金を織り込んでいない
- 運用益・配当への課税（約20%）を引いていないため、楽観側に出る
- 将来の支出変化（子の独立、医療費の増加）を含んでいない
- 精度を競う数字ではなく、**今のペースが目標に対して速いか遅いかを見るための計器**

## 6. 自動では取れないもの

| 項目 | 取得方法 | 更新頻度 |
|------|---------|---------|
| 現金預金 / 証券 / 年金資産 | MFの「資産」画面から転記 | 月1回 |
| 不動産評価額 | 査定サイトの概算 | 年1回 |
| 住宅ローン残高 | 返済予定表 | 年1回 |

不動産とローンは前月値を引き継ぎ、1年以上更新がなければその旨を添えるだけにする。

## 7. 数字を出したあとの態度

振り返りスキルと同じく、**評価しない。**

- 「支出が多い」「もっと節約できる」と言わない。求められたときだけ答える
- 前月比が悪化していても、それ自体を問題として指摘しない
- 数字が悪い月ほど、背景（特別な支出、収入の端境期）を先に聞く

家計の数字は自己評価に直結する。責められる場所になった時点で、記録は止まる。
止まった家計簿からは何も分からないので、続くことが正確さより優先する。

## 8. Routineと実行順序

家計の集計を月初に走らせると、**カードの利用確定が間に合わず数字が欠ける**。
そのため実行日をずらし、家計 → 月次 → 四半期 の順に並べてある。

| Routine | 日（JST） | trigger_id |
|---------|----------|-----------|
| 📈 家計の月次集計 | 毎月8日 20:00 | `trig_01KZbsCyf7BoJLV1HvvdwziE` |
| 📙 月次の振り返り | 毎月10日 20:00 | `trig_01MxHzaePkdfemv9dWPBzqbz` |
| 📕 四半期の振り返り | 1/4/7/10月の11日 20:00 | `trig_01CuWBEpoMBivMnG3gFaB2VL` |

月次の振り返りは家計サマリーを読み、💰の目標レビューのときに3指標を事実として提示する。

### 要対応

📈 家計の月次集計 Routine には **Notion と Google ドライブの両方**のコネクタが要る。
CLIからは付与できないため、claude.ai の Routines 画面で設定する（手順は
`docs/reflection-design.md` の「既知の制約（Notionコネクタ）」と同じ）。
